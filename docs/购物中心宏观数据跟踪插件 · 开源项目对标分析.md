# 开源项目对标分析：监控维度、数据源与数据获取方式

对标对象：调研笔记中列出的 6 组开源项目（7 个仓库）。
分析方法：全部仓库已克隆到本地，做静态代码分析；未安装、未运行任何项目。例外：对国家统计局的公开数据接口做了一次在线连通性验证（只读 HTTP 请求，不涉及任何仓库安装）。验证日期：2026-10-10。

---

## 一、逐仓库分析

### 1. space-lumps/macro-financial-indicators（★ 架构参照）

- **监控维度**：8 个美国宏观指标（M2、美元指数、2Y/10Y 国债收益率、10Y-2Y 利差、VIX、CPI、联邦基金利率）。面向加密市场，维度少而精。
- **数据源**：FRED 唯一来源。
- **更新机制**：GitHub Actions 每日 09:00 UTC 运行 Python ETL，把每个指标的全量历史写成 `data/*.json`，有变更则自动提交；前端是纯静态 GitHub Pages + Chart.js，直接 fetch 本地 JSON。## 参考意义，此更新机制可以参考，我们在本地运行，要嘛在我的NAS要么在闲置的电脑。每日爬取，清洗后符合要求的数据入库，然后分析。##
- **数据格式**：每个指标一个 JSON 文件，含全量历史点；缺失值存 `null`，不做零填充；带 `_meta.generated_utc` 生成时间戳。
- **可借鉴点**：

1. "定时 ETL → 数据落成静态 JSON → 前端只渲染"的三层分离，与 Obsidian 离线场景完全兼容，与我们确认稿的架构方向一致。
2. 缺失存 `null` 而非 0，与我们第 4 节规则 5 一致。
3. 每张图表配一段"该指标对市场意味着什么"的说明文字，直接对应我们"指标关联笔记"的诉求。

- **与我们规则的差异**：它每次全量覆盖 JSON 文件（数据源是 FRED 权威源，修订由 FRED 自己处理）。##参考价值 是的，我坚持这一点，只增不改##我们的"只增不改、修订追加版本"规则仍然正确，因为中国数据经由二手聚合渠道（东财、新浪），必须自己处理修订。

### 2. tduic/macro-dashboard（卡片交互设计）

- **监控维度**：全球跨资产行情（股指、利率、汇率、能源、农产品、加密）+ 美国经济数据发布 + 新闻聚合。面向交易员，不是宏观研究。
- **数据源**：yfinance（行情）、FRED REST（经济序列）、RSS（新闻）。无数据库，内存 TTL 缓存（行情 60 秒、FRED 6 小时、新闻 10 分钟）。
- **指标定义方式**：声明式冻结 dataclass 分两类规格——`RateSpec`（利率类，变动以基点表示）和 `ReleaseSpec`（发布类，含 FRED release_id 用于经济日历）。## 参考价值：这种对数据更新的分类值得借鉴 ##
- ## 参考价值，后面可以作为前端呈现的参考之一吧，但我没有直接看过，不太确定必要性多高 ##**可借鉴点**（这是本仓库最有价值的部分，全部为前端算法，可直接移植到我们的呈现层）：

1. **新鲜度判定**（`staleness.ts`）：不知道每个数据源的精确发布日，按频率推定阈值——月度数据距今 ≤40 天为新鲜、>75 天为过期；日度数据 ≤1 天新鲜、≤4 天宽容（周末）、之后过期。返回 fresh/weekend/stale 三态用于界面标色。
2. **异常检测**（`anomaly.ts`）：对 sparkline 取对数收益率，用最近约 30 个点（排除最新一点）做基线，最新变动超 ±2σ 标 warn、±3σ 标 extreme。全部在客户端完成，不需要后端。
3. 卡片三件套：当前值 + 1Y/2Y 百分位仪表（"处于一年高位/低位"）+ 距高点回撤。
4. 经济日历：用 FRED 的 release_id 查询官方发布日程，实现"发布日历与采集状态可视化"的直接参照。

### 3. bbrigmga/macro-dashboard（指标注册表）

- **监控维度**：13 个宏观指标卡 + 增长/通胀象限图 + 14 只美股的隐含/实现波动率表。面向美股投资者。
- **数据源**：FRED + Yahoo Finance。每晚 GitHub Actions 抓取波动率数据写入 SQLite。
- **核心可借鉴点**：`indicator_registry.py` 是我们"指标注册表"概念的最完整范本。每个指标一条声明式配置（IndicatorConfig），字段包括：

| 字段 | 作用 |
| --- | --- |
| key / display_name | 标识与展示名 |
| fred_series / yahoo_series | 数据源序列，一个指标可挂多个序列 |
| chart_type / value_column / periods / frequency | 展示规格（图型、取数列、回溯期、频率） |
| bullish_condition / threshold | 预警方向与阈值（低于/高于/递减 + 数值） |
| warning_description | 每个指标自带的长文本解读，含操作手册式建议 |
| cache_ttl / fetch_in_batch | 缓存策略、是否批量抓取 |
| custom_chart_fn / custom_status_fn | 自定义图表与状态逻辑的钩子（ dotted path ） |

- ## 值得借鉴，这一个点非常重要，我们的指标不只是拿来看看而已，更重要的是所谓的指征信号，单一指标不容易有指征作用，但多个指标叠加就更容易体现，似乎有交叉验证的意义## 另一个值得注意的设计：预警信号不只靠单指标阈值，还有**组合危险信号**（PMI 低于 50 + 周度失业申领连升 3 周 + 工时下降，三者同时成立才触发"保护资本"提示）。这对应我们"餐饮 vs 商品增速差""M1-M2 剪刀差"这类组合判断，可以在呈现层预留组合规则位。
- `release_schedule.py` 维护"指标 → 序列 → release_id → 下次发布日期"的映射，与我们"发布日历"需求完全对应（国内可换成各发布机构的日程表）。

### 4. wzx11223344/econ-dashboard（五页结构 + 中国数据源）

- **监控维度**：中美日德英印 6 国，20+ 指标；三页结构（宏观概览 / 中国经济高频跟踪 / 跨国比较）。与我们的"全国概览 → 城市深度 → 指标对比"结构同源。
- **数据源**：World Bank API + FRED（经 pandas-datareader，免 key）+ akshare（中国数据，免 key）。缓存用 Streamlit 的 `st.cache_data`，TTL 1800–3600 秒。
- **## 借鉴价值，在通过akshare官网或者github仓库验证akshare接口有效、数据有效之前，不要直接使用akshare## 重要教训（负面）**：该仓库调用的 akshare 函数名（`ak.china_cpi_monthly`、`ak.china_retail_sales_yoy`、`ak.china_money_supply` 等）与 akshare 真实 API（`macro_china_cpi_monthly`、`macro_china_consumer_goods_retail`、`macro_china_money_supply` 等）大面积不符，几乎每个中国数据调用都会被 `except` 吞掉并记一行 warning，界面上悄悄变空。**结论：这个仓库的中国数据链路实际从未工作过，其代码不能照抄。** 借鉴它等于借鉴一个假象——我们分析时逐条核实了函数名（见下节）。
- 结构层面可借鉴：三页信息架构、`_clean_china_monthly` 一类"原始 DataFrame → 规范时间序列"的清洗层设计。

### 5. akfamily/akshare + akfamily/aktools（中国数据基础设施，重点）

akshare 是中国宏观数据的事实标准。我们逐条核对了确认稿中每个指标在 akshare 的覆盖情况，并对国家统计局接口做了在线实测。**这是本次分析对 PRD 影响最大的一节。**

| 我们的指标 | akshare 覆盖 | 接口 | 验证结论 |
| --- | --- | --- | --- |
| 社零总额 | ✓ | `macro_china_consumer_goods_retail`（东方财富） | 有总量+同比+环比+累计 |
| 社零分项（限上 16 类） | ✓ | `macro_china_nbs_nation`（国家统计局直连） | **实测连通**。目录含：总额、按经营地分、按消费类型分（商品零售 vs 餐饮收入）、限上商品零售 16 个分项、网上零售额、服务零售额。数据期可检索到当月（2026-10）。比我们原方案"统计局网页抓取"更稳 |
| 餐饮 vs 商品增速 | ✓ | 同上（按消费类型分） | 实测目录在，一键取得 |
| M1、M2 | ✓ | `macro_china_money_supply`（东方财富） | M0/M1/M2 数量 + 同比 + 环比 |
| M1-M2 剪刀差 | ✓ | 上两条计算得出 | 呈现层衍生 |
| 住户存款、非金融企业存款 | ✗ | 无 | 全库无"住户"维度接口。**缺口**。央行官网金融数据新闻稿解析，或维持手动 |
| 住户短贷/中长贷 | ✗ | 只有 `macro_china_new_financial_credit`（新增人民币贷款总量） | 无住户结构。**缺口**，同上 |
| CPI | ✓ | `macro_china_cpi` | 全国+分地区月度 |
| 核心 CPI | 待验证 | 国家统计局"价格指数"目录大概率有 | 工程实施时验证 |
| DR007 / DR001（存款类机构） | ✗ | 只有 `repo_rate_hist`（FDR001/FDR007 回购定盘利率，外汇交易中心）和 SHIBOR | DR 无覆盖。维持中国货币网抓取；**备选**：用 FDR007 近似（走势接近但不同源，需注明） |
| 省/市社零（上海、四川、成都） | ✗ | `macro_china_nbs_region`（分省接口） | **实测：目录在，但数据止于 2010-12，已停更**。分省月度社零国家库不再发布，只能各省自采。**确认维持原方案**：省市统计局官网/新闻通稿轮询 |
| 城轨客运量 | ✗ | `macro_china_society_traffic_volume` 为全国全社会客货运量（新浪源） | 非城轨、非城市级。维持交通运输部月度速报 |
| 上海金融数据 | — | 无 | 维持手动 |
| 机构季报 PDF | — | 无 | 维持手动 |

**关于国家统计局接口的实测细节**（重要，影响实现）：

- 接口地址 `data.stats.gov.cn` 的 `queryIndexTreeAsync` + `esData` 两个端点，POST JSON 即可取数，无需 key。
- akshare 的 `macro_china_nbs_nation(kind="月度数据", path="国内贸易 > 社会消费品零售总额", period="202401-")` 一行取数；path 支持多级目录，16 个分项各有叶子节点。
- 两个工程注意点：① 实测返回中指标名字段为 null（新版本接口变化），实现时应固定 indicatorIds 的顺序做位置解析，并在入库校验时核对数值口径；② 该接口依赖浏览器指纹（akshare 内部用 curl_cffi 模拟 Chrome），直接 requests 调用可能被拦，建议直接用 akshare 或沿用其 curl_cffi 会话。
- `period` 参数实测 `"LAST3"` 等简写不可用，需传 `"202605MM-202610MM"` 这种显式区间。

**aktools**：把 akshare 全部接口包成本机 FastAPI（`python -m aktools` 起在 8080 端口，`/api/public/<函数名>?参数`）。意义：Obsidian/TypeScript 插件可以不经过 Python ETL、直接 fetch 本机 HTTP 取得中国数据。注意：默认无鉴权、需本机常驻运行； NBS 新接口能否走 aktools 取决于安装的 akshare 版本。

### 6. JovaniPink/awesome-economic-data（数据源目录）

- **内容**：113 个数据源的结构化目录（JSON catalog），每个源带主题分类、方法论说明、获取限制、证据状态。用途是"指标选品参考书"。
- **对我们的实际价值有限**：0 个中国数据源，消费高频代理（Visa 消费动能、OpenTable 就餐、TSA 出行）全部美国本土。宏观 dashboard 生态确实如调研笔记所说，90% 面向美股/加密。
- **可借鉴**：它的"数据源准入评审清单"格式（每个源必须写清局限、更新频率、获取限制）可以直接搬用为我们插件的数据源登记规范。
- 中国语境下的对应物（地铁客流、拥堵指数、平台消费指数）均属日度粒度，已在确认稿第 6 节列为非目标，第一版不需要。

## 二、对照结论：指标体系与获取方式的修订建议

### 1. 指标体系不需要增加维度，但有两处可以增强

开源项目验证了我们的"少而精"方向是对的—— curated 项目（econdash 20 个、space-lumps 8 个、 bbrigmga 13 个）都集中在个位数到 20 个指标。**不建议因为开源项目有什么就加什么。**两处值得考虑的增强：

1. **##此条建议，我采纳## 网上零售额、服务零售额**（国家统计局目录有现成叶子节点）：网上零售与实体购物中心是竞争关系，其增速差是业态判断的直接输入；服务零售额是 2023 年起的新官方口径，与我们"餐饮 vs 商品"的服务消费判断互补。成本极低（同一接口多取两个叶子）。
2. **消费类型分项按经营地（城镇/乡村）**：对成都这类能级城市的购物中心参考意义一般，优先级低于上一条，列为可选。

### 2. 数据获取方式的修订（相对确认稿第 3 节）

| 数据 | 确认稿原方案 | 修订后（经开源项目验证） |
| --- | --- | --- |
| CPI | 自动 | 自动，用 akshare `macro_china_cpi`；核心 CPI 实施时验证 NBS 目录 |
| 社零及分项 | 自动（未指明通道） | 自动，**改用 akshare NBS 直连接口**：总额+16 分项+餐饮/商品+网上零售一次搞定，比网页抓取稳定 |
| M1/M2 | 自动（央行） | 自动，用 akshare `macro_china_money_supply`（东财聚合）；如有合规顾虑可并行保留央行官网抓取做交叉校验 |
| 住户存贷款 | 自动（央行） | **降级为半自动**：akshare 无覆盖，央行新闻稿结构不固定，第一版建议"抓取全文 + 人工确认入库" |
| DR007/DR001 | 自动（中国货币网） | 维持；**增加备选**：akshare 的 FDR007（定盘利率）可作为备用通道，主通道失败时切换并注明口径差异 |
| 省/市社零 | 自动轮询，超时转手动 | 维持。另获实证支持：NBS 分省月度社零 2010 年已停更，省市数据只能省级自采，轮询+手动兜底是正确设计 |
| 城轨客运量 | 自动或半自动 | 维持交通运输部速报半自动 |
| 上海金融、机构季报 | 手动 | 维持 |

### 3. 架构与数据处理规则的强化建议（融合各仓库经验）## 这些建议我全部接受 ##

1. **指标注册表**（融合 bbrigmga #3 + tduic #2）：每个指标一条声明式配置，建议字段：key、显示名、层级（大势/本地/辅助）、地区编码、来源类型（NBS 接口/东财接口/央行/手动）、抓取函数与参数（path、indicatorIds）、发布节奏、新鲜度阈值（fresh/stale 天数，借鉴 tduic）、预警规则（阈值/趋势/组合，借鉴 bbrigmga 的组合危险信号思路）、解读文本、扩展预留位。新增指标 = 新增一条注册表记录 + 地区编码，与确认稿"扩展只需新增地区编码"一致。
2. **修订处理**：space-lumps 的全量覆盖模式不适合我们（二手源）。确认稿"只增不改 + 增量版本"维持不变，工程实现为：每次抓取全量序列 → 与库内最新版本 diff → 有变更才追加新版本。
3. **异常标记双阈值**（确认稿规则 6 的具体化）：同比/环比波动超历史 ±2σ 标"待确认"（借鉴 tduic 的 z-score 法，基线排除当期值，避免当期值拉高自身基线）。
4. **新鲜度三态**：fresh/临期/stale 阈值写进注册表（月度指标：≤40 天 fresh、>75 天 stale 可作初值），驱动发布日历与采集状态可视化的标色，与确认稿第 5 节末条呼应。
5. **采集层形态**：Python ETL（本机定时或 GitHub Actions）→ 数据落成 JSON/CSV → 插件只渲染文件（space-lumps 模式）；aktools 作为插件直连的备选通道。两者共用同一个指标注册表，避免双份定义漂移。
6. **图表说明文字**：每个指标在注册表里带一段"该指标对购物中心意味着什么"（space-lumps、bbrigmga 都这么做），直接服务月度判断笔记场景。

### 4. 诚实的边界说明 ## 此处列举的事项后续需继续论证 ##

- 以上对 akshare 覆盖度的结论基于仓库源码核对 + 一次 NBS 接口实测；东财系接口（货币供应、社零总量）本次未实测连通，实施时应先跑通再写进 PRD 的验收标准。
- 核心 CPI 的 NBS 目录覆盖"待验证"。
- 4 个仪表盘项目（#1/#2/#3/#4）均无中国省市级数据实践，本地层（上海/四川/成都）的采集方案没有开源先例可抄，轮询设计需要在第一版后根据实际失败率调参。
- tduic 与 bbrigmga 面向高频交易场景，其"日度新鲜度""对数收益率异常"算法对我们月度为主的场景只能借用思想，阈值必须重定。
